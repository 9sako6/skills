# 出力形式

次のひな形の構造を守って出力してください。`<...>` は中身に置き換え、「無ければ省く」とある行や節は、該当が無ければ書かないでください。

````markdown
## Findings

### <番号>. <High|Medium|Low>: <何がまずいかの要約>

```diff
- <今の形。構造の本質が分かる最小限の行>
+ <直した後の形。どこに置くかもコメントで添える>
```

- **箇所**：
  - <diff の行と同じ識別子や短い語>: <作業ディレクトリからのパス>:<行>（<ref>）
- **負担**：<このままだと、変更する人が何を余計に背負うか>
- **範囲**：<この PR でどこまでやるか。無ければ省く>

## Good Points

- <根拠を確認できた健全な点>

## Next

1. <優先順位、検証結果、残る判断事項。無ければ節ごと省く>
````

## 書き方

### diff

- 今と直した後を合わせて 6 行程度までにしてください。実際のコードを写し切らず、`...` やコメントで省いて構造の違いだけを残してください
- 直した後の姿は diff だけで示し、ほかの行で繰り返さないでください。完成したコードのようには書かず、方向が分かる姿にとどめてください
- コードでない対象（運用手順、モデル、UI など）でも、今と直した後を diff の形で並べてください

### 箇所

- 1 か所を 1 行にしてください。パスは作業ディレクトリからの相対で、ファイル名と行を省略しないでください。パスはバッククォートで囲まないでください
- 末尾には、どの ref の行か（PR、master など）を添えてください。手元の作業ツリーがその ref ではないときは、Next でそのことを伝えてください
- ファイルでない箇所（文書の節、図の要素など）は、パスの代わりに辿れる場所を書いてください
- 規約に基づく指摘では、根拠となる規約もここに書いてください

### 負担

- 所有・依存・状態・インターフェースの観点名は判断に使い、出力には書かないでください。変更する人が何に困るかの具体で伝えてください

### Good Points

- 例: 境界が保たれている、契約テストが効いている、責務が既存の所有者に収まっている、不要な公開契約が増えていない

## 例

作業ディレクトリが /work で、todo リポジトリが /work/todo にあり、PR のブランチを手元に取り込んでいない場合の 1 件:

````markdown
### 1. Medium: 読み込みの状態を、組み合わせが自由なフィールドで持っている

```diff
- type state = { loading : bool; error : string option; items : todo list option }
- if s.loading then ... else match s.error, s.items with ...
+ type state = Loading | Failed of string | Loaded of todo list
+ (* 表示は match で分岐する。loading と error が同時にある状態は作れない *)
```

- **箇所**：
  - state: todo/lib/state.ml:3（PR）
  - render: todo/bin/view.ml:18（PR）
- **負担**：loading と error が同時にあるなど、ありえない組み合わせを読む側がそれぞれ想定することになる。分岐の順番を変えると表示が変わる
- **範囲**：この PR では state の型だけを変え、ほかの画面は後続でよい
````
